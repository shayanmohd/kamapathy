# Security model

Kamapathy is an early desktop browser project. It uses Electron's Chromium engine and isolation controls, but it has not been independently audited. This document describes the implementation boundaries and remaining limitations.

## Remote pages and browser controls

Remote pages run in native `WebContentsView` instances with Node.js integration disabled, context isolation enabled, and renderer sandboxing enabled. Only the local browser shell receives the preload bridge. Remote content must not receive native browser actions or access to the automation API. Every http or https frame of a page also runs Kamapathy's form script, in an isolated world and without Node.js. It exposes nothing to the page, reports a sign-in form only while the person controls that space, and never acts while an agent has control; [Saved passwords](#saved-passwords) covers what it reports and what gets filled.

The address bar accepts HTTP and HTTPS pages, search text, and the internal new tab destination. Unsupported schemes and credential bearing URLs are rejected, with the refusal "Kamapathy opens web addresses and files only." Loopback HTTP addresses remain available for local development. A `file:` address of a type Kamapathy shows opens only in a personal space no agent can reach, and local HTML and SVG load with JavaScript off, so a local page cannot script the browser it opened in. An extension's own pages open under the same rule, only in personal spaces and only while that extension is installed. Agents open HTTP, HTTPS and `about:blank` only, by one rule for every address they ask for, in a navigation, a new page or a reload: a `file:`, `data:`, `blob:` or `view-source:` URL, any other scheme and an address carrying credentials are refused with that address and a hint, there is no filesystem read path, and `about:blank` holds no data. A server redirect out of that rule is cancelled and reported to the agent as a failed navigation with the address it refused. A `referer` an agent sends affects only its own navigation, must be an HTTP or HTTPS address without credentials, and is not stored. These controls do not classify the trustworthiness of a website.

Native IPC checks the sending renderer and its main frame. A popup that a page opens with `window.open`, a link or a form becomes a tab in its opener's space, keeps its opener there and uses the opener's session, with the same sandboxing and isolation as any tab, so a page never opens a popup into another space. Popups may show only `about:blank`, web pages without credentials, or `blob:` URLs a web page made; `data:` and other schemes are refused, and the browser window itself opens no popups. There is no popup blocker: these scheme limits and the tab limits bound a flood of popups. Every space asks for site permissions in Kamapathy's own prompt bar above the page, which replaces the native permission box; only the person's answer there ends a request, one request at a time and the oldest first. Microphone and camera grants are separate, and every grant is keyed by space, origin, and permission, so a grant in one space never applies to another even when the two share a session. A personal space's Allow or Block is saved for that space, origin and permission and can be removed in Settings, while an agent space's answer lasts only while the space is open. Pending permission responses are rejected after their space is deleted or the page changes. A USB or HID chooser grants the one device the person picked and only until Kamapathy quits; serial ports and Bluetooth devices are refused in this build. Server and proxy sign-ins and client certificate requests are asked for in the same bar: Kamapathy never answers a sign-in itself and never picks a certificate, it sends none without the person, and a request with no page behind it gets none. In a tab an agent controls, a location, notification, camera, microphone or MIDI request reaches the person only when it arrives within 5000 ms of one of the agent's own routes; every other request is refused, and the agent learns no more than its origin and permission. Those spaces keep only a download an agent armed for its own tab, and cancel the rest as before. A link to another application, such as `mailto:` or a meeting link, asks the person every time with a native "Open <App>?" box that names the site asking, and it opens nothing unless they choose Open while the page is still the one that asked; one request is taken per page at a time. Agent spaces and granted personal spaces block these links outright, and 27 schemes, among them `file:`, `javascript:`, `data:`, `shell:` and `search-ms:`, are never handed to another application from any space.

Kamapathy presents Chrome's reduced user agent to every page and request, with no Electron or application token, so sites see a Chromium browser of its engine's major version. Google may still block authentication in the embedded desktop engine. The rejection-page notice offers a human-clicked default-browser action through trusted shell IPC, a Copy link action that uses the main process's clipboard, and the import panel, so a sign-in made in another browser can be brought over instead. It opens only a fixed public Google or Play Console URL for the active rejected tab, without forwarding authentication parameters, cookies, or credentials, and it opens nothing while Kamapathy is the default browser, where the notice drops that action anyway, since the link would come straight back. The agent API has no external-browser route, no clipboard route and no import route. This does not authenticate the Kamapathy session.

Kamapathy can register itself as this user's web browser and as a viewer for the file types it shows, from Settings or the last welcome step. The registration is per user: on Windows the installer writes those keys and the uninstaller removes exactly them, and no platform claims a file type as its default handler. Links and files other applications hand over open as the person's tabs in a personal space no agent can reach, never in the active space when an agent could reach it; at most 20 items are taken from one hand-over, and a burst of system events is rate limited. Because any link can now start Kamapathy with arguments, packaged builds turn off Electron's run-as-Node fuse, the `NODE_OPTIONS` fuse and Node's command-line inspector arguments, and the registered command hands the link over as a single argument that cannot be read as switches. Nothing in the agent API registers the browser or reads that status.

A PDF shows in Chromium's own viewer in every space. The viewer's extension frames are blocked for agents: they are never entered, listed or attached to. An agent reads a PDF's text through one route, which fetches the bytes again in the tab's own session and never replays a form submission, and withholds the text if the person takes over or stops the agent while it reads. Parsing runs in a separate utility process with no eval path, no network access, a heap cap and a deadline the parent enforces, and it reads one document before it exits. The extracted text is untrusted page content, like a snapshot's text.

## Spaces and local data

Spaces share one persistent Electron session partition by default, `persist:space-personal`, so a sign-in made in any shared space, including an agent space, is available in every other shared space. A space with separate sign-ins uses a partition of its own: a persistent one for a personal space, a temporary in-memory one for an agent space that disappears when Kamapathy quits. Separate sign-ins are chosen per space, when it is created or later from the Spaces popover, and the Isolate agent spaces setting under Settings, Agents, makes every new agent space separate; the automation API can also ask for one isolated space. Session handlers for permissions and downloads are attached per partition and resolve the space from the page that asked, so an agent space on the shared session still holds its permission requests for the person and keeps only downloads an agent armed, and permission grants stay keyed by space, origin, and permission. Deleting a space clears storage and cache only for a partition that belonged to that space alone; the shared partition is never cleared by deleting a space. An agent can clear one site's cookies, storage or cache, and nothing clears a whole session. In an isolated agent space the clear runs at once, since no one else uses that partition. In a session the person uses, the shared one or a granted personal space's own, the site must be loaded in the agent's tab or one of its frames, and Kamapathy holds the space for the person, which shows it as **Needs you**, and asks above that tab, "Clear data for <host>?", with how many cookies would go and the sites the person would be signed out of, or, when no cookie would go, that sites may forget their settings. Only the person's **Clear** clears anything: **Don't clear**, no answer in time, a takeover, Stop, a closed tab, agent access going off and a client that disconnects each end the request with nothing cleared. The request lives only in memory, and neither the agent's answer nor activity names a cookie or its value. When the person keeps an agent space as a personal space after its agent finished or was stopped, a space with separate sign-ins leaves its temporary partition, which is discarded, and its pages reload in a new persistent partition of its own. Space separation is session separation inside one desktop application. It does not isolate operating system accounts or provide a separate virtual machine.

Bookmarks, history, settings, and restored personal tabs are written to the app's user data directory. An import from another browser reads that browser's bookmark and history files, and its cookies when the person asks for sign-ins, copying a locked database to a temporary folder that is deleted afterwards, and never changes the other browser. Safari is read only from the file Safari exports, which the person chooses themselves. Chromium stores cookies and site storage within that profile. Saved passwords are kept in an encrypted vault of their own, described under [Saved passwords](#saved-passwords); Kamapathy adds no other encrypted vault for application state. Downloaded files remain on disk after a space or tab closes. Clearing history does not erase downloaded files, cookies, or other site storage.

A download an agent armed is written instead under `agent-downloads` in that user data directory, in a folder only this account can enter and a file only this account can read. It never reaches the person's Downloads folder or their downloads list, Kamapathy never opens it, and it is removed when its space closes, when agent access goes off, at quit, at the next start and an hour after it finished. The site permissions a person answered in their own spaces are written to the state file, at most 1000 of them, and are read back only for spaces that still exist, web origins and permission names Kamapathy knows. Waiting requests, device grants and anything typed into a sign-in prompt are never written to disk.

Importing sign-ins is the person's own action in the app. It is not on the agent socket, no agent route or action can start it, and one import runs at a time. Reading another browser's cookies needs its encryption key, and on macOS the system asks for the person's password once per browser, which is the consent for that browser; a refusal skips that browser's sign-ins and still imports its bookmarks and history. Sign-ins sent to the shared session reach every space that shares sign-ins, and so the agent spaces there while agent access is on; the alternative, a new personal space per profile, keeps them in a partition of their own, which is the contained choice. Cookie values are written straight into Chromium partitions and are never stored anywhere else, never written to the state file, and never printed in logs, activity or warnings. On Windows, cookies Chrome bound to its own application are not imported, so those sign-ins have to be made again here.

The activity feed is visible runtime state, not an immutable audit log. An application restart clears it. Avoid treating it as evidence that all activity on a page has been recorded.

## Saved passwords

One vault per profile holds every saved password, at `<userData>/passwords/vault.bin`, in a folder with mode 0700 and a file with mode 0600. The file is the marker `KPV1` followed by the login list sealed with Electron's safe storage key, which is "Kamapathy Safe Storage" in the macOS keychain, a DPAPI key on Windows and a libsecret or KWallet secret on Linux. Without a system keyring nothing is saved at all. Inside that sealed list each password and note is sealed again, so the main process opens one value at a time, and writes go through a temporary file and a rename, leaving the previous file in place when a write fails. No password, origin, username or note is written to `browser-state.json`, printed in logs or warnings, shown in the activity feed or sent over the agent socket; the shell receives a password only when the person asks to see one, and a copy is written to the clipboard by the main process. A vault holds at most 10000 logins and 1000 never-saved sites, with an origin of at most 2048 characters, a realm of 256 and a username, password or note of 1000.

The vault's boundary is the operating system account, the same boundary as the rest of this document. On Windows and Linux any program running as the person, an agent's own scripts included, can ask the same keyring for that key and decrypt the file. On macOS the keychain asks the person first, and a denied prompt leaves the vault locked until they allow it. Keeping passwords here is therefore safer than a plain text file and no safer than the account itself.

Showing, copying, editing or exporting a password asks the person to authenticate again first: Touch ID where the computer offers it, with the account password as its fallback, and elsewhere a native "Show passwords?" confirmation, which does not stop someone already sitting at an unlocked computer. A check that passed within the last 60 seconds is reused. A shown password hides itself again after 60 seconds, and a copied password leaves the clipboard after 60 seconds if it is still the copied value.

Kamapathy never fills a password when a page loads. A fill happens only after the person chooses a login in a native menu that pages can neither cover nor open, it goes only to the frame that reported the field, and only when that frame's origin matches the login's. From then on the value is page content: scripts in the page, including scripts an agent left running, can read it, which is why the person is asked first in a space agents can use.

No agent surface reaches any of this. No route, client method, CLI command, script global, site pack helper or CDP method touches the vault, the prompts or the fill menu, and such paths answer `404 route_not_found` like any other unknown route. The menu, the save prompts and the Passwords dialog are native or shell interface, so they never appear in snapshots, frame lists, screenshots or events. While an agent has control of a space, the form script reports nothing, so agent input opens no menu, fills nothing and captures nothing, and nothing an agent types, fills or passes as HTTP credentials is ever saved. In a space agents can use, once the person has control, filling a password and using a saved HTTP sign-in each ask for confirmation first, because an agent can read that page.

Import and export are the person's own actions in the app, on shell IPC behind the sender check: neither the CLI nor the agent socket can start them. An import from another browser reads copies of that browser's files with that browser's own key, which on macOS means its keychain approval, and a browser whose rows cannot be read is reported as a warning instead. Importing a CSV file offers to move that file to the Trash afterwards, since it holds passwords in plain text. An export warns before it writes, and writes the file with mode 0600; anyone who can open that file can read every password in it.

Nothing about saved passwords touches the network. There are no leak checks, no site icons fetched for a login, no affiliation service and no sync.

## Local automation

The automation API is on by default and can be turned off in Settings, under Agents; a saved choice to turn it off is kept. It listens only on a Unix socket inside a private per-profile directory, or on a Windows named pipe with a new random name each start, and never on a network port. There is no token: the trust boundary is your operating system account. Any program running as you can use the API while it is on, and other accounts cannot open it. The server also rejects browser Origin and Sec-Fetch requests and does not enable CORS. The bundled client refuses agent files and folders that another account could read or replace, and sends no command until the server returns the random instance value Kamapathy recorded privately at start, so a program that later takes over a socket or Windows pipe name receives nothing. When agent access is off, the client never starts Kamapathy. Automatic starts run only a recorded program whose path no other account can write, and never open a debugging port.

The API can access spaces it created and spaces the user explicitly grants to that running connection. Agent spaces use the shared session unless the Isolate agent spaces setting is on or the agent asked for an isolated space, so an agent can act on the sites the person is signed in to, inside a space the person can see. A personal space becomes reachable only through the person's own click in Kamapathy, **Let an agent use this space** in its options or **Allow** on an agent's request; the API itself can only ask. Request text is stripped of control and bidirectional characters and always shown as the agent's, at most 3 requests wait at once, and none are taken for 60 seconds after a decline, so a local program cannot flood the person with them. While granted, the whole space follows agent rules: history pauses for the person's own tabs there too, a site permission request in any of its tabs follows the rule for a tab an agent controls, only a download an agent armed is kept, and the agent can run its own scripts in the tabs it manages there while Page scripts is on. Every tab already open stays the person's, with no debugger session and no agent input, until the agent adopts it. A grant ends when the agent finishes, at Stop, when agent access is turned off and when Kamapathy quits, and it is never saved.

Agent text is bounded and cannot pass for Kamapathy's own words. The labels, status text, failure messages and space names an agent writes go through one cleaner: line breaks, tabs and the line and paragraph separators become spaces, other control characters, DEL and the bidirectional marks are removed, runs of whitespace collapse and the ends are trimmed. Each field has a limit that applies to the raw value, 60 characters for a label, 120 for a status, 300 for a failure message and 48 for a name, and a value over its limit, or a label, message or name that cleans away to nothing, is refused with `400 invalid_field`. What survives is shown as the agent's: quoted in menus, notifications and the quit question, styled apart from Kamapathy's own phrases in the agent bar, the Spaces menu and activity, and never placed in a button, a link, the address bar, the window title, a dialog or a prompt. Kamapathy's own reasons never take that style. Labels and status may echo page or task details, so they live only in memory with the rest of the agent's runtime state, are never saved or restored, and never leave the computer; Kamapathy never derives a label from a value an agent filled, and the skill forbids field values, secrets and personal data in them.

The agent cursor is a view of Kamapathy's own, not page content. It loads one fixed local file with no preload, no IPC, no network and no navigation, under a content security policy that allows nothing but its own script and style, and it receives only cleaned text as JSON. Websites cannot see it or reach it, and page screenshots do not contain it. It is drawn only over the page of an agent-owned space the person is looking at, and it hides under human control, with agent access off, while the window is hidden or the page is frozen, and while the person's own pointer is over it.

Page reads and actions require agent ownership and a page the agent manages. The UI exposes activity and lets the user take control, after which subsequent agent operations in that space are denied until control returns to the agent. The user can return it in the interface, or an agent can take it back after a takeover or a handoff through the `resume` route, which reaches only those same spaces and records an activity entry. Taking control therefore pauses an agent that follows the skill's guidance, but it does not stop a program that ignores it. **Stop**, in the agent bar or the space's details, does: it ends the agent's access to that one space whoever has control, and every later request there, `resume` included, is refused with `space_ended` until the person grants the space again. Finishing a space and closing it never close tabs the person opened. Turning agent access off is the hard stop for every space: the server refuses every request, including `resume`, every grant ends, and after access is turned on again it does not reclaim earlier spaces without a new grant.

Closing the window does not stop agents while agent access is on: it hides instead, always on macOS, where applications run without a window, and on Windows and Linux while an agent space or a granted space is open. The agent spaces, their pages, their debugger sessions and the socket stay as they were, so grants and the instance remain valid. The person's own ungranted pages are closed as a close closes them, so nothing of theirs keeps running unseen, and the tray icon on Windows and Linux, the Dock menu on macOS, a second launch and the first notification all bring the window back. Screenshots keep working while the window is away, as they do while it is minimized. Agents continue only while agent access is on, and turning it off remains the hard stop.

A quit while a space is the agent's own, or waiting for the person, asks first and names the spaces. A confirmed quit stops the agents and writes a private marker in the profile's agent folder that holds only the time of the quit; for ten minutes the bundled client refuses to start Kamapathy and tells the agent to ask the person first, and every start removes the marker. The person's decision to stop agents is therefore not undone by the next command, while a program that ignores the client still cannot reach anything until Kamapathy runs again.

The API supports bounded DOM snapshots, navigation, trusted clicks, double clicks, hovers, drags, keys and chords, field filling, option choices, focus, file selection, scrolling, waits for a URL, a load state, an element state or a page function, sequential batches, a mouse and a keyboard per tab whose input state lives in the main process and never in the page, pasting without the system clipboard, and screenshots of the agent tab's viewport, full page or a region. It does not expose Node.js or a general filesystem interface, and an agent's own code reaches a page only as a page script or a protocol command, described below, which run while the Page scripts setting is on and nowhere else. No agent-written code runs in the main process: a URL glob is matched by a bounded matcher that cannot backtrack, and a script's own RegExp or predicate runs in the agent's Node.js, never here. A wait sees only its own tab: the pages that tab opened, its own frames' requests and its own addresses. A page's leave guard is overridden only under agent control, and every override is reported to the agent and in Recent activity. The person in control is always asked, with a Leave site question they answer themselves. Bounds hold these open-ended operations down: 60 seconds for a navigation or a wait, four of them in flight per tab, 2,048 characters per URL glob and 32 retained commits per page. Each route accepts only the body fields it declares and refuses any other field before the request waits for its turn. Its DOM operations cover the main document, open shadow roots and frames from any web origin, including embedded payment and sign-in forms; extension, PDF viewer, local file and internal frames and closed shadow roots are not entered. Agents once could only list a frame from another origin; they now read it and act in it, and Recent activity names the frame's host when they do. On the shared session an embedded frame can show an account you are signed in to elsewhere, and the agent can read and use it, as it could by opening that site itself. Batches check ownership between steps and report completed actions when a later action fails. Navigation invalidates refs and cancels prepared snapshot, focus, click, or drag results that belong to the previous document. When a page replaces a ref's element, the ref can follow the control drawn in its place, but only on the same document and URL, only to an element with the same tag, role, type, label, group question, and surrounding text that no other ref holds, only when the control looked like no other visible control when it was listed, and only when exactly one element matches or the match is at the same position in the page. The response names every ref that moved. File-input refs are never re-bound by any action, so files reach only the input an agent observed. A control drawn with no size is clicked with an untrusted DOM click only when its surroundings are on screen and uncovered, and the response says so. An HTML drag is intercepted so that Chromium never starts an operating system drag, and it is cancelled if the person takes over. Snapshots show current field values so agents can check their work, including values a person typed during a handoff. Password inputs, fields whose autocomplete marks a current or new password, a one-time code, or payment card data, and masked fields report only that a value is hidden, in every frame. Website text can still echo a hidden value, so this is not comprehensive redaction.

Trusted clicks and keys carry the buttons, keys and modifiers that tab holds, which is what makes a chord a chord, and a release lets all of them go: on a cross-document main-frame navigation, after 60 seconds without an input request and on the release route, which a run sends for every page it touched, while a takeover, a **Stop** and agent access going off release the keys alone, so a drag in progress is not dropped halfway. Agent input never touches the system clipboard, the window's shortcuts, an application menu role, the native context menu or native pickers. A copy, cut or paste chord is refused before any key is sent, held modifiers included, and on Linux so is a middle press over an editable, which would paste the primary selection. A paste instead goes through a `DataTransfer` Kamapathy builds for that one event and offers the page, which may take it; nothing is read from or written to the clipboard the person uses, and Kamapathy never inserts the HTML itself. Input in flight is recorded per tab, so the shell skips a key event matching an agent key, keeps unhandled agent keys out of menu roles, opens no native context menu while agent input is in flight on the tab or for 1000 ms after unless the person's own input arrived since, and never activates a split pane from an agent's mouse. Input that would open a native select, color or date picker is refused and names the action to use instead.

Extension frames, Chromium's PDF viewer and Kamapathy's own internal pages refuse agent input even with `force`: the node under a point is read before anything is pressed, and a point, or the frame holding focus, outside the web page is refused, so an extension's inline interface and the viewer stay the person's alone. Every input command is authorized for the space before it is sent, the page-side work is fixed isolated-world code, and after a takeover only key releases and the drag cancel go out, so nothing new reaches a page the person has taken back. Typed, inserted and pasted text never appears in a result, an error or the activity feed, and page text an error quotes, such as the element that covered a target, is capped and stripped of control and bidirectional characters.

Kamapathy holds one internal Chrome DevTools Protocol session on each tab an agent manages while the agent controls its space, through Electron's debugger API. Its code refuses Target and Browser commands on that session, apart from attaching to the tab's own page and frames, so it cannot list or reach other tabs, windows or the browser interface. Role selectors and snapshot locators add fixed accessibility queries on that same session: `Accessibility.getFullAXTree` once per frame, with `DOM.resolveNode` and `DOM.describeNode` for the nodes they name, and Kamapathy ends the tab's accessibility state and releases those nodes after each pass. Other tabs never get one, and it is released when you take over or stop the agent, when the agent releases the page or finishes, when the space closes or when you turn agent access off.

Agents can now also run their own scripts in the tabs they manage, while **Page scripts** is on in Settings, under Agents, as it is by default. A script runs in the page's main world without a user gesture and reads whatever the page can, including values snapshots hide, cookies without HttpOnly and stored tokens; in a space that shares sign-ins those are the person's, as the setting's note says. An in-page fetch runs in Kamapathy's isolated world in the main frame, under the page's own origin, cookies, content security policy and CORS, and never through a request path that skips CORS; it reaches only an HTTP or HTTPS address without credentials or a `blob:` URL of the page's own origin. While Page scripts is off, every script, fetch, protocol command and event read answers `403 agent_scripts_off`, and turning it off fails the calls in flight and withholds their results, closes the agent's protocol sessions, cancels in-page fetches and stops event recording. Clearing a site's data, described under Spaces and local data, is not behind this switch. A script an agent evaluates is stopped at its execution limit, one second before the call's own timeout of at most 60 seconds. Chromium normally gives an agent tab and a personal tab separate renderers, but it can put tabs of one site in one renderer once it reaches its process limit, and a busy agent script could then stall the person's tab until that limit stops it.

Protocol commands an agent sends go to sessions of its own, which Kamapathy opens on the tab's own page and its out-of-process frames beside the session it keeps for itself, and agents never see a session id. A deny-by-default policy passes only the commands of that tab's page. It blocks the Target, Browser, SystemInfo, Tethering and Tracing domains, the storage domains that reach every site's data, the debugging and profiling domains that pause or read a renderer, and the commands that reach files, devices, credentials, certificates or the person's own prompts, answers to HTTP and proxy sign-ins included, each with `403 cdp_method_blocked` and its reason. The space's own protocol route answers two commands itself, `Target.getTargets`, listing only that space's tabs, and `Browser.getVersion`, refuses the rest and sends nothing to Chromium. Object and context ids must be ones the tab gave the agent, a context id only on the page or frame that gave it, and a binding must name such a context. Kamapathy's own worlds, Electron's preload world, which holds the channel for password forms, and the person's extensions' are never given, an agent can take neither Kamapathy's nor Electron's world names, in any spacing or case, nor make a world that reaches other origins, and a navigation it sends must name an HTTP or HTTPS address. Input commands go out through Kamapathy's own input dispatcher on its session, never on an agent session, so the window's shortcuts and menus do not react to them. A mouse, touch, tap, scroll or pinch point in an extension or internal frame, or less than a pixel from one, keys and text sent while the focus is in such a frame, and a press that would open a native picker are refused, and so are drag commands, which could carry local files, and emulation that changes the page's scale or viewport, which would move where input lands. No input command an agent may send reaches the system clipboard, in either direction, but after a user activation a page's own script, an agent's included, can still write to it. Cookie export is closed: the protocol's cookie commands are blocked, and an event log shows each cookie value as `(hidden)`. A takeover, any hold for the person, Stop, Page scripts or agent access going off and a closed or released tab end the agent's sessions, with the emulation, interception, scripts and bindings they set, and recording pauses while the person has control, so nothing they type enters the log. Recent activity notes that a script ran, a fetch went out or protocol commands were sent, the last at most once a minute per tab, and never records a script, its data or a cookie value.

In a tab an agent controls, Kamapathy replaces `alert`, `confirm` and `prompt` in the page's main world with a fixed handler of its own, so no website can hold a dialog box on the person's screen and no page is left waiting for an answer. It dismisses by default and accepts only what an agent armed before the action, and a dialog that goes around it is answered through the tab's own protocol session. The handler is Kamapathy's own code rather than an agent's script, so the Page scripts setting does not gate it, and it is in place only while the agent controls the tab: once the person has it, the page's own functions are back and they see Electron's own boxes. A page can detect the handler, read an armed policy including its prompt text, remove the channel it reports through and report dialogs it never showed, so a dialog record is untrusted data, like page text.

Scripts and the REPL run as the agent's own account in the agent's own Node.js, never inside Kamapathy, so they never receive Kamapathy's operating system permissions, and they reach Kamapathy only through the same socket and routes. Values from a workspace `.env` or an `--env-file` reach only the script's `process.env`: a Kamapathy the client starts does not inherit them, the client never prints, logs or sends them, and a `.env` cannot change the profile, the workspace or the app the client starts. A workspace or env file that another account could change is refused, so no other account can feed a script its variables; Windows skips these ownership checks, as it does for the agent folder. Code given through `run -` or `run -e` goes to a temporary file created exclusively with mode 0600 and always removed, and the TypeScript re-run on older Node.js passes the child a path, never code. REPL history stays in memory. After a takeover, a handoff, the person's Stop or agent access going off, a run withholds its output so the agent does not act on it, but that is not a security boundary: Kamapathy's ownership checks are, and a program that ignores the client can still call `resume` after a takeover. `GET /health` tells programs running as you Kamapathy's version and API level, its Electron, Chromium, Node and V8 versions, the folder of the skill it ships and any newer release it has found; it holds no space, tab or page data and still refuses browser requests. Syntax hints come from `node --check`, which parses the agent's own script file with the agent's own Node.js, without `NODE_OPTIONS`, and never runs it.

Site packs and a workspace `helpers.mjs` are code of the same kind. A pack's Node tools and `helpers.mjs` run in the agent's own Node.js as the person's account, with full Node access, like the agent's scripts; a pack's page tools run in the agent's page as page scripts, with that space's sign-ins and everything a page script can read, and are refused while Page scripts is off. Pack code runs only when a script calls one of its tools, when `run` or the REPL loads `helpers.mjs`, or when `kamapathy sites check` imports a pack's Node tools, so a pack from elsewhere deserves review before it goes into the workspace. Kamapathy's app never reads the workspace or loads a pack, and packs add no route, socket, setting or permission. The client reads a workspace pack or `helpers.mjs` only when no part of its path is a link and, on macOS and Linux, every part belongs to the account and no other account can change it, so another account cannot plant code a later run executes; Windows skips the ownership check and refuses a path that leads outside its folder instead. Node loads a tool's own imports without these checks, so they belong inside the pack. A pack should hold no secrets or personal data, since later agents read its notes, and `kamapathy sites check` refuses bidirectional controls that can disguise code.

File selection accepts supplied bytes for a current file-input ref. The local client reads 1 to 8 selected regular files totaling at most 16 MiB, then transfers their basenames, MIME types, and bytes through the local agent socket. The API handles those bytes in memory and does not accept paths to read from the browser machine. Only the three file routes permit a 24 MiB JSON body; a paste permits 192 KiB and other requests remain limited to 64 KiB. One transfer can be pending at a time, with ownership and document checks before it reaches the input. The input must be visible or hidden inside visible parent UI; inert, aria-hidden, disabled, and directory inputs are rejected. File selection is not a batch operation.

Selecting files dispatches input and change events and can immediately transmit them to the website. The user's authorization must cover the selected files and destination before that command runs. Taking control cannot retract bytes already sent to a site. Responses and activity report selection counts rather than file contents or local paths; the website still receives basenames and bytes and can display or retain them. Verify a site's final receipt before treating selection as a completed upload, and inspect its state before any retry.

`setInputFiles` takes any selector or ref, including one that matches a hidden element, retargets from a label or from the single file input inside the match, and accepts 0 to 8 files under the same bounds; an empty list clears the input. Agent-controlled tabs always intercept the file chooser, so no native panel can open on the person's screen: an action that opens a chooser nothing armed closes it, gives the input the cancel event a person's own cancel sends and fails with `file_chooser_opened`, and only a chooser an agent armed takes files, from the bytes the client sent. Files still travel as bytes alone. No route reads or returns a path on the browser machine, and directory pickers and native file handles stay unsupported.

An agent may store a name and password for up to eight http or https origins of its own space. They cross the socket the way a `fill` value already does, answer the first server challenge from exactly that origin in that space's agent-controlled pages, live in memory only, never appear in a response, in activity or in a log, and are cleared when the space closes or agent access goes off. A repeated challenge, any proxy challenge and every client certificate request go to the person instead, and a challenge from a subresource of another origin is cancelled.

Any program running under your account can exercise the API's allowed capabilities while agent access is on, and because agent spaces share your sign-ins by default, that now includes acting as you on the sites you are signed in to and, while Page scripts is on, reading what those pages hold. Only run agents and tools you trust, turn Page scripts off to keep agents to snapshots and actions, and turn agent access off when you do not want local programs driving agent spaces. The socket is not a defense against an already compromised local account.

The Isolate agent spaces setting and a space's own separate sign-ins exist for that reason: they give an agent a temporary session without your sign-ins. Neither undoes actions an agent performs on a remote website. A form submission or purchase remains an external action. Review the [automation guide](automation.md) for the precise endpoints, ownership checks, and validation limits.

## Extensions

Only the person installs, imports, turns on or off, pins or removes an extension, through the shell and native dialogs. The agent API has no extension route, and nothing an agent does adds one. A Chrome Web Store install leaves its staging folder only after every proof passes: the CRX3 header's shape, every signature in it over the header and the archive, a publisher proof whose key matches the Chrome Web Store key hash pinned in Kamapathy, an ID derived from the developer key that equals the ID the person asked for, and the manifest checks. The `key` written into the manifest is that verified developer key, so the extension keeps the ID the store gave it. An import reads another browser's profile read only and brings none of the extension's data with it, and component extensions such as the PDF viewer get no bridge, while no unpacked folder or import can take their IDs.

Extensions load only into persistent sessions: the person's spaces and the agent spaces that share their sign-ins. An agent space with a temporary session of its own, from **Isolate agent spaces** or an isolated space the API asked for, never loads one. In a shared session an extension reads and changes agent pages and sees agent traffic, as it does the person's own pages, so for an untrusted extension or sensitive work the advice is isolation.

Extensions cannot reach the browser shell, the agent socket, another session, the password vault or a debugger. The shell's preload goes only to the browser interface, the agent API listens on a socket with no network port for a page to open, a bridged call is answered from the session it came from, so an extension sees only that session's tabs and windows, and no debugger API is bridged to it.

The bridged `chrome` members come from two preloads Kamapathy registers on extension sessions, one for pages and one for service workers. Each acts only in a `chrome-extension:` page or worker of an extension loaded in that session, never in a component extension's, and installs its members before the extension's own code runs. A call is answered only when it comes from that extension's own main frame, its action popup, one of its windows or its worker in that session, and only up to 64 KiB of JSON at a time. Everything else on the channel is refused.

Agents cannot use extension interfaces. An extension's frame is opaque to them: it is listed as a blocked entry with the extension's name, is never entered or read, and input that lands there is refused. Protocol commands into an extension's frame or content-script world are refused as out of scope, and a popup or an extension window is not a tab, so no route reaches it. An agent therefore cannot pull secrets out of a password manager extension or approve a request in a wallet. Extension names, at 75 characters, titles, at 200, and badge text, 4 characters of which are shown, are cleaned like agent text before the interface shows them.

Installs and update checks go to Google without cookies, in a session of their own. They send the extension IDs and versions, the Chromium version, the operating system and the architecture, as Chrome does. The check runs once a day while extensions are installed and can be turned off in Settings, under Extensions. There is no telemetry.

## Agent setup

Set up agents is opt in. Until the person chooses **Set up**, nothing outside Kamapathy's own profile changes. Setup then copies the skill that ships inside the app into a private tools folder, `~/.local/share/kamapathy` with mode 0700 or `%LOCALAPPDATA%\Kamapathy\tools`, keyed by the version and a digest of the skill's files, and points a stable `skill` folder there. A tools folder that is a link, or owned by another account, stops setup. For each agent the person ticked it creates a link named `kamapathy` in that agent's own skills folder, and, when those boxes are ticked, a launcher plus `~/.local/bin/kamapathy` or a PATH entry for its `bin` folder on Windows, and a marked block in one shell startup file. Every effect is a checkbox the person can see, another tool's own copy of the skill is replaced only row by row and only after being renamed to a timestamped backup beside it, and one lock file lets one Kamapathy do this work at a time. Each start refreshes the stable folder so the skill matches the running browser, and it never recreates an entry the person deleted.

Remove setup deletes only entries that link to Kamapathy's stable folder, Kamapathy's own command link, blocks holding exactly Kamapathy's text and a PATH entry equal to its own `bin` folder, then the tools folder itself. It never follows a link to delete inside another folder, and backups stay.

Agents read the skill as instructions, so the tools folder is private to the account. A program already running as the person can still change it, which is the same boundary as the rest of this document. The Codex rule is a separate option that starts unticked: it adds `prefix_rule(pattern=["kamapathy"], decision="allow")` between Kamapathy's markers in `${CODEX_HOME:-~/.codex}/rules/default.rules`, and the panel says what that means. Codex may then run every `kamapathy` command without asking, including `run`, which executes code the agent wrote in its own Node.js, and `upload`, which sends local files to a website, so browser actions can reach past Codex's own network sandbox. The shell probe that reports whether the command is on PATH runs the person's shell startup files, and only while they have the panel open.

Agent setup and the macOS move to Applications make no network requests. The install scripts contact only GitHub over HTTPS, without identifiers, and check every download against that release's `SHA256SUMS.txt`. A checksum protects the transport, not a compromised release, until the signer is pinned. The scripts never use sudo on macOS and never add or remove a quarantine attribute.

## Updates

The only requests Kamapathy's updater makes are a release list, once a day or when asked, and, on request, an installer and its `SHA256SUMS.txt`. They run in an in memory session that sends no cookies, credentials, referrer or cached data, with `User-Agent: Kamapathy` and no version: no identifier, usage data or telemetry. GitHub sees the address and the time, and each installer download adds to GitHub's public count for that file. Certificate errors fail with no exception.

Downloads use HTTPS and URLs fixed to the configured repository's release. The file must match the size the API reported, and its SHA-256 must equal both the release's `SHA256SUMS.txt` and GitHub's own digest; Kamapathy hashes the file again before opening it. Builds are unsigned, so whoever controls the repository's releases could publish a bad installer with matching checksums. That is the same trust as any website download, and it is why Kamapathy never installs by itself.

Kamapathy writes the installer itself rather than through Chromium's download manager, so the file carries no `com.apple.quarantine` attribute or Mark of the Web and Gatekeeper or SmartScreen may not ask again. The install dialog keeps their steps in case they do.

Agents may read the update status, ask for a check and start a download. Opening, installing, cancelling and quitting exist only on shell IPC behind the sender check, so only the person's own click installs anything. A program running as the person could still open the downloaded file, which is inside the account boundary this document describes. Release text is never rendered: the window shows validated versions, sizes and fixed URLs, file names come from the installer naming rule rather than the network, and What's new ships with the app. Release notes open only in a personal space no agent can read. The update test variables are ignored in packaged builds and stripped from starts the client makes.

## Privacy

Kamapathy has no account and no telemetry. It never reports usage, errors or page data anywhere. Its own outbound requests are the ones named above: the daily release check and, when asked, an installer and its checksum file. Both carry no identifier, and the check can be turned off in Settings, under Updates. Once extensions are installed, the daily Chrome Web Store update check above joins them, carrying their IDs and versions, and it can be turned off in Settings, under Extensions. Everything else leaves the computer because a page or the person asked for it. The install scripts and the website's download buttons read only public release data. History, bookmarks, spaces and settings stay in the profile folder on the computer.

## Release work

Development artifacts are unsigned. Kamapathy can download an update, and the person installs it: while releases are unsigned nothing installs itself, and the installer opens only from the person's own click in Settings. Keep Electron and other dependencies current during development. The signing plan is prepared and dormant: `electron-builder.signed.yml` extends the packaging configuration with a Developer ID identity, the hardened runtime, notarization and `build/entitlements.mac.plist` on macOS, and Azure Trusted Signing on Windows. CI packages with it only once the signing secrets exist, then verifies the signatures, and publishing requires that step once the repository variable `KAMAPATHY_SIGNED_RELEASES` is `true`. Until signing is in place the scripts cannot pin a signer, and a production release still needs broader operating system testing and a security review of browser and automation boundaries.

Kamapathy does not currently provide a phishing reputation service or an audited privacy mode. Its separate spaces are not a claim of anonymous browsing.

## Reporting a vulnerability

Use the repository's private vulnerability reporting feature if it is available. Otherwise contact the repository owner through their published contact details and ask for a private reporting channel. Do not publish exploit details or personal profile data in a public issue before maintainers have had a chance to assess the report.

Include the affected Kamapathy version, operating system, minimal reproduction steps using nonpersonal test data, and the boundary you believe is bypassed. Never attach a real browser profile or session cookie.
