# Security model

Kamapathy is an early desktop browser project. It uses Electron's Chromium engine and isolation controls, but it has not been independently audited. This document describes the implementation boundaries and remaining limitations.

## Remote pages and browser controls

Remote pages run in native `WebContentsView` instances with Node.js integration disabled, context isolation enabled, and renderer sandboxing enabled. Only the local browser shell receives the preload bridge. Remote content must not receive native browser actions or access to the automation API.

The address bar accepts HTTP and HTTPS pages, search text, and the internal new tab destination. Unsupported schemes and credential bearing URLs are rejected, with the refusal "Kamapathy opens web addresses and files only." Loopback HTTP addresses remain available for local development. A `file:` address of a type Kamapathy shows opens only in a personal space no agent can reach, and local HTML and SVG load with JavaScript off, so a local page cannot script the browser it opened in. An extension's own pages open under the same rule, only in personal spaces and only while that extension is installed. These controls do not classify the trustworthiness of a website.

Native IPC checks the sending renderer and its main frame. A popup that a page opens with `window.open`, a link or a form becomes a tab in its opener's space, keeps its opener there and uses the opener's session, with the same sandboxing and isolation as any tab, so a page never opens a popup into another space. Popups may show only `about:blank`, web pages without credentials, or `blob:` URLs a web page made; `data:` and other schemes are refused, and the browser window itself opens no popups. There is no popup blocker: these scheme limits and the tab limits bound a flood of popups. Personal spaces ask for site permissions through a native prompt. Microphone and camera grants are separate, and every grant is keyed by space, origin, and permission, so a grant in one space never applies to another even when the two share a session. Pending permission responses are rejected after their space is deleted or the page changes. Agent spaces, and personal spaces while an agent may use them, deny permission requests and downloads. A link to another application, such as `mailto:` or a meeting link, asks the person every time with a native "Open <App>?" box that names the site asking, and it opens nothing unless they choose Open while the page is still the one that asked; one request is taken per page at a time. Agent spaces and granted personal spaces block these links outright, and 27 schemes, among them `file:`, `javascript:`, `data:`, `shell:` and `search-ms:`, are never handed to another application from any space.

Kamapathy presents Chrome's reduced user agent to every page and request, with no Electron or application token, so sites see a Chromium browser of its engine's major version. Google may still block authentication in the embedded desktop engine. The rejection-page notice offers a human-clicked default-browser action through trusted shell IPC, a Copy link action that uses the main process's clipboard, and the import panel, so a sign-in made in another browser can be brought over instead. It opens only a fixed public Google or Play Console URL for the active rejected tab, without forwarding authentication parameters, cookies, or credentials, and it opens nothing while Kamapathy is the default browser, where the notice drops that action anyway, since the link would come straight back. The agent API has no external-browser route, no clipboard route and no import route. This does not authenticate the Kamapathy session.

Kamapathy can register itself as this user's web browser and as a viewer for the file types it shows, from Settings or the last welcome step. The registration is per user: on Windows the installer writes those keys and the uninstaller removes exactly them, and no platform claims a file type as its default handler. Links and files other applications hand over open as the person's tabs in a personal space no agent can reach, never in the active space when an agent could reach it; at most 20 items are taken from one hand-over, and a burst of system events is rate limited. Because any link can now start Kamapathy with arguments, packaged builds turn off Electron's run-as-Node fuse, the `NODE_OPTIONS` fuse and Node's command-line inspector arguments, and the registered command hands the link over as a single argument that cannot be read as switches. Nothing in the agent API registers the browser or reads that status.

A PDF shows in Chromium's own viewer in every space. The viewer's extension frames are blocked for agents: they are never entered, listed or attached to. An agent reads a PDF's text through one route, which fetches the bytes again in the tab's own session and never replays a form submission, and withholds the text if the person takes over or stops the agent while it reads. Parsing runs in a separate utility process with no eval path, no network access, a heap cap and a deadline the parent enforces, and it reads one document before it exits. The extracted text is untrusted page content, like a snapshot's text.

## Spaces and local data

Spaces share one persistent Electron session partition by default, `persist:space-personal`, so a sign-in made in any shared space, including an agent space, is available in every other shared space. A space with separate sign-ins uses a partition of its own: a persistent one for a personal space, a temporary in-memory one for an agent space that disappears when Kamapathy quits. Separate sign-ins are chosen per space, when it is created or later from the Spaces popover, and the Isolate agent spaces setting under Settings, Agents, makes every new agent space separate; the automation API can also ask for one isolated space. Session handlers for permissions and downloads are attached per partition and resolve the space from the page that asked, so an agent space on the shared session still denies permission requests and downloads, and permission grants stay keyed by space, origin, and permission. Deleting a space clears storage and cache only for a partition that belonged to that space alone; the shared partition is never cleared by deleting a space. When the person keeps an agent space as a personal space after its agent finished or was stopped, a space with separate sign-ins leaves its temporary partition, which is discarded, and its pages reload in a new persistent partition of its own. Space separation is session separation inside one desktop application. It does not isolate operating system accounts or provide a separate virtual machine.

Bookmarks, history, settings, and restored personal tabs are written to the app's user data directory. An import from another browser reads that browser's bookmark and history files, and its cookies when the person asks for sign-ins, copying a locked database to a temporary folder that is deleted afterwards, and never changes the other browser. Safari is read only from the file Safari exports, which the person chooses themselves. Chromium stores cookies and site storage within that profile. Kamapathy does not add an encrypted vault for application state. Downloaded files remain on disk after a space or tab closes. Clearing history does not erase downloaded files, cookies, or other site storage.

Importing sign-ins is the person's own action in the app. It is not on the agent socket, no agent route or action can start it, and one import runs at a time. Reading another browser's cookies needs its encryption key, and on macOS the system asks for the person's password once per browser, which is the consent for that browser; a refusal skips that browser's sign-ins and still imports its bookmarks and history. Sign-ins sent to the shared session reach every space that shares sign-ins, and so the agent spaces there while agent access is on; the alternative, a new personal space per profile, keeps them in a partition of their own, which is the contained choice. Cookie values are written straight into Chromium partitions and are never stored anywhere else, never written to the state file, and never printed in logs, activity or warnings. On Windows, cookies Chrome bound to its own application are not imported, so those sign-ins have to be made again here.

The activity feed is visible runtime state, not an immutable audit log. An application restart clears it. Avoid treating it as evidence that all activity on a page has been recorded.

## Local automation

The automation API is on by default and can be turned off in Settings, under Agents; a saved choice to turn it off is kept. It listens only on a Unix socket inside a private per-profile directory, or on a Windows named pipe with a new random name each start, and never on a network port. There is no token: the trust boundary is your operating system account. Any program running as you can use the API while it is on, and other accounts cannot open it. The server also rejects browser Origin and Sec-Fetch requests and does not enable CORS. The bundled client refuses agent files and folders that another account could read or replace, and sends no command until the server returns the random instance value Kamapathy recorded privately at start, so a program that later takes over a socket or Windows pipe name receives nothing. When agent access is off, the client never starts Kamapathy. Automatic starts run only a recorded program whose path no other account can write, and never open a debugging port.

The API can access spaces it created and spaces the user explicitly grants to that running connection. Agent spaces use the shared session unless the Isolate agent spaces setting is on or the agent asked for an isolated space, so an agent can act on the sites the person is signed in to, inside a space the person can see. A personal space becomes reachable only through the person's own click in Kamapathy, **Let an agent use this space** in its options or **Allow** on an agent's request; the API itself can only ask. Request text is stripped of control and bidirectional characters and always shown as the agent's, at most 3 requests wait at once, and none are taken for 60 seconds after a decline, so a local program cannot flood the person with them. While granted, the whole space follows agent rules: history pauses for the person's own tabs there too, and downloads and permission prompts are denied. Every tab already open stays the person's, with no debugger session and no agent input, until the agent adopts it. A grant ends when the agent finishes, at Stop, when agent access is turned off and when Kamapathy quits, and it is never saved.

Agent text is bounded and cannot pass for Kamapathy's own words. The labels, status text, failure messages and space names an agent writes go through one cleaner: line breaks, tabs and the line and paragraph separators become spaces, other control characters, DEL and the bidirectional marks are removed, runs of whitespace collapse and the ends are trimmed. Each field has a limit that applies to the raw value, 60 characters for a label, 120 for a status, 300 for a failure message and 48 for a name, and a value over its limit, or a label, message or name that cleans away to nothing, is refused with `400 invalid_field`. What survives is shown as the agent's: quoted in menus, notifications and the quit question, styled apart from Kamapathy's own phrases in the agent bar, the Spaces menu and activity, and never placed in a button, a link, the address bar, the window title, a dialog or a prompt. Kamapathy's own reasons never take that style. Labels and status may echo page or task details, so they live only in memory with the rest of the agent's runtime state, are never saved or restored, and never leave the computer; Kamapathy never derives a label from a value an agent filled, and the skill forbids field values, secrets and personal data in them.

The agent cursor is a view of Kamapathy's own, not page content. It loads one fixed local file with no preload, no IPC, no network and no navigation, under a content security policy that allows nothing but its own script and style, and it receives only cleaned text as JSON. Websites cannot see it or reach it, and page screenshots do not contain it. It is drawn only over the page of an agent-owned space the person is looking at, and it hides under human control, with agent access off, while the window is hidden or the page is frozen, and while the person's own pointer is over it.

Page reads and actions require agent ownership and a page the agent manages. The UI exposes activity and lets the user take control, after which subsequent agent operations in that space are denied until control returns to the agent. The user can return it in the interface, or an agent can take it back after a takeover or a handoff through the `resume` route, which reaches only those same spaces and records an activity entry. Taking control therefore pauses an agent that follows the skill's guidance, but it does not stop a program that ignores it. **Stop**, in the agent bar or the space's details, does: it ends the agent's access to that one space whoever has control, and every later request there, `resume` included, is refused with `space_ended` until the person grants the space again. Finishing a space and closing it never close tabs the person opened. Turning agent access off is the hard stop for every space: the server refuses every request, including `resume`, every grant ends, and after access is turned on again it does not reclaim earlier spaces without a new grant.

Closing the window does not stop agents while agent access is on: it hides instead, always on macOS, where applications run without a window, and on Windows and Linux while an agent space or a granted space is open. The agent spaces, their pages, their debugger sessions and the socket stay as they were, so grants and the instance remain valid. The person's own ungranted pages are closed as a close closes them, so nothing of theirs keeps running unseen, and the tray icon on Windows and Linux, the Dock menu on macOS, a second launch and the first notification all bring the window back. Screenshots keep working while the window is away, as they do while it is minimized. Agents continue only while agent access is on, and turning it off remains the hard stop.

A quit while a space is the agent's own, or waiting for the person, asks first and names the spaces. A confirmed quit stops the agents and writes a private marker in the profile's agent folder that holds only the time of the quit; for ten minutes the bundled client refuses to start Kamapathy and tells the agent to ask the person first, and every start removes the marker. The person's decision to stop agents is therefore not undone by the next command, while a program that ignores the client still cannot reach anything until Kamapathy runs again.

The API supports bounded DOM snapshots, navigation, trusted clicks, double clicks, hovers, drags, keys and chords, field filling, option choices, focus, file selection, scrolling, conditional waits, sequential batches, a mouse and a keyboard per tab whose input state lives in the main process and never in the page, pasting without the system clipboard, and screenshots of the agent tab's viewport, full page or a region. It does not expose arbitrary JavaScript evaluation, Node.js, or a general filesystem interface. Each route accepts only the body fields it declares and refuses any other field before the request waits for its turn. Its DOM operations cover the main document, open shadow roots, and same-origin frames; a frame from another origin is listed by its title, name, or host and refuses every action, and closed shadow roots are not entered. Batches check ownership between steps and report completed actions when a later action fails. Navigation invalidates refs and cancels prepared snapshot, focus, click, or drag results that belong to the previous document. When a page replaces a ref's element, the ref can follow the control drawn in its place, but only on the same document and URL, only to an element with the same tag, role, type, label, group question, and surrounding text that no other ref holds, only when the control looked like no other visible control when it was listed, and only when exactly one element matches or the match is at the same position in the page. The response names every ref that moved. File-input refs are never re-bound by any action, so files reach only the input an agent observed. A control drawn with no size is clicked with an untrusted DOM click only when its surroundings are on screen and uncovered, and the response says so. An HTML drag is intercepted so that Chromium never starts an operating system drag, and it is cancelled if the person takes over. Snapshots show current field values so agents can check their work, including values a person typed during a handoff. Password inputs, fields whose autocomplete marks a current or new password, a one-time code, or payment card data, and masked fields report only that a value is hidden. Website text can still echo a hidden value, so this is not comprehensive redaction.

Trusted clicks and keys carry the buttons, keys and modifiers that tab holds, which is what makes a chord a chord, and a release lets all of them go: on a cross-document main-frame navigation, after 60 seconds without an input request and on the release route, which a run sends for every page it touched, while a takeover, a **Stop** and agent access going off release the keys alone, so a drag in progress is not dropped halfway. Agent input never touches the system clipboard, the window's shortcuts, an application menu role, the native context menu or native pickers. A copy, cut or paste chord is refused before any key is sent, held modifiers included, and on Linux so is a middle press over an editable, which would paste the primary selection. A paste instead goes through a `DataTransfer` Kamapathy builds for that one event and offers the page, which may take it; nothing is read from or written to the clipboard the person uses, and Kamapathy never inserts the HTML itself. Input in flight is recorded per tab, so the shell skips a key event matching an agent key, keeps unhandled agent keys out of menu roles, opens no native context menu while agent input is in flight on the tab or for 1000 ms after unless the person's own input arrived since, and never activates a split pane from an agent's mouse. Input that would open a native select, color or date picker is refused and names the action to use instead.

Extension frames, Chromium's PDF viewer and Kamapathy's own internal pages refuse agent input even with `force`: the node under a point is read before anything is pressed, and a point, or the frame holding focus, outside the web page is refused, so an extension's inline interface and the viewer stay the person's alone. Every input command is authorized for the space before it is sent, the page-side work is fixed isolated-world code, and after a takeover only key releases and the drag cancel go out, so nothing new reaches a page the person has taken back. Typed, inserted and pasted text never appears in a result, an error or the activity feed, and page text an error quotes, such as the element that covered a target, is capped and stripped of control and bidirectional characters.

Kamapathy holds one internal Chrome DevTools Protocol session on each tab an agent manages while the agent controls its space, through Electron's debugger API. Its code refuses Target and Browser commands on that session, apart from attaching to the tab's own page and frames, so it cannot list or reach other tabs, windows or the browser interface. Role selectors and snapshot locators add fixed accessibility queries on that same session: `Accessibility.getFullAXTree` once per frame, with `DOM.resolveNode` and `DOM.describeNode` for the nodes they name, and Kamapathy ends the tab's accessibility state and releases those nodes after each pass. Other tabs never get one, and it is released when you take over or stop the agent, when the agent releases the page or finishes, when the space closes or when you turn agent access off.

Scripts and the REPL run as the agent's own account in the agent's own Node.js, never inside Kamapathy, so they never receive Kamapathy's operating system permissions, and they reach Kamapathy only through the same socket and routes. Values from a workspace `.env` or an `--env-file` reach only the script's `process.env`: a Kamapathy the client starts does not inherit them, the client never prints, logs or sends them, and a `.env` cannot change the profile, the workspace or the app the client starts. A workspace or env file that another account could change is refused, so no other account can feed a script its variables; Windows skips these ownership checks, as it does for the agent folder. Code given through `run -` or `run -e` goes to a temporary file created exclusively with mode 0600 and always removed, and the TypeScript re-run on older Node.js passes the child a path, never code. REPL history stays in memory. After a takeover, a handoff, the person's Stop or agent access going off, a run withholds its output so the agent does not act on it, but that is not a security boundary: Kamapathy's ownership checks are, and a program that ignores the client can still call `resume` after a takeover. `GET /health` tells programs running as you Kamapathy's version and API level and its Electron, Chromium, Node and V8 versions; it holds no space, tab or page data and still refuses browser requests. Syntax hints come from `node --check`, which parses the agent's own script file with the agent's own Node.js, without `NODE_OPTIONS`, and never runs it.

File selection accepts supplied bytes for a current file-input ref. The local client reads 1 to 8 selected regular files totaling at most 16 MiB, then transfers their basenames, MIME types, and bytes through the local agent socket. The API handles those bytes in memory and does not accept paths to read from the browser machine. Only the upload route permits a 24 MiB JSON body; a paste permits 192 KiB and other requests remain limited to 64 KiB. One transfer can be pending at a time, with ownership and document checks before it reaches the input. The input must be visible or hidden inside visible parent UI; inert, aria-hidden, disabled, and directory inputs are rejected. File selection is not a batch operation.

Selecting files dispatches input and change events and can immediately transmit them to the website. The user's authorization must cover the selected files and destination before that command runs. Taking control cannot retract bytes already sent to a site. Responses and activity report selection counts rather than file contents or local paths; the website still receives basenames and bytes and can display or retain them. Sites requiring trusted native chooser events or native file handles are outside this action's support. Verify a site's final receipt before treating selection as a completed upload, and inspect its state before any retry.

Any program running under your account can exercise the API's allowed capabilities while agent access is on, and because agent spaces share your sign-ins by default, that now includes acting as you on the sites you are signed in to. Only run agents and tools you trust, and turn agent access off when you do not want local programs driving agent spaces. The socket is not a defense against an already compromised local account.

The Isolate agent spaces setting and a space's own separate sign-ins exist for that reason: they give an agent a temporary session without your sign-ins. Neither undoes actions an agent performs on a remote website. A form submission or purchase remains an external action. Review the [automation guide](automation.md) for the precise endpoints, ownership checks, and validation limits.

## Agent setup

Set up agents is opt in. Until the person chooses **Set up**, nothing outside Kamapathy's own profile changes. Setup then copies the skill that ships inside the app into a private tools folder, `~/.local/share/kamapathy` with mode 0700 or `%LOCALAPPDATA%\Kamapathy\tools`, keyed by the version and a digest of the skill's files, and points a stable `skill` folder there. A tools folder that is a link, or owned by another account, stops setup. For each agent the person ticked it creates a link named `kamapathy` in that agent's own skills folder, and, when those boxes are ticked, a launcher plus `~/.local/bin/kamapathy` or a PATH entry for its `bin` folder on Windows, and a marked block in one shell startup file. Every effect is a checkbox the person can see, another tool's own copy of the skill is replaced only row by row and only after being renamed to a timestamped backup beside it, and one lock file lets one Kamapathy do this work at a time. Each start refreshes the stable folder so the skill matches the running browser, and it never recreates an entry the person deleted.

Remove setup deletes only entries that link to Kamapathy's stable folder, Kamapathy's own command link, blocks holding exactly Kamapathy's text and a PATH entry equal to its own `bin` folder, then the tools folder itself. It never follows a link to delete inside another folder, and backups stay.

Agents read the skill as instructions, so the tools folder is private to the account. A program already running as the person can still change it, which is the same boundary as the rest of this document. The Codex rule is a separate option that starts unticked: it adds `prefix_rule(pattern=["kamapathy"], decision="allow")` between Kamapathy's markers in `${CODEX_HOME:-~/.codex}/rules/default.rules`, and the panel says what that means. Codex may then run every `kamapathy` command without asking, including `run`, which executes code the agent wrote in its own Node.js, and `upload`, which sends local files to a website, so browser actions can reach past Codex's own network sandbox. The shell probe that reports whether the command is on PATH runs the person's shell startup files, and only while they have the panel open.

Agent setup and the macOS move to Applications make no network requests. The install scripts contact only GitHub over HTTPS, without identifiers, and check every download against that release's `SHA256SUMS.txt`. A checksum protects the transport, not a compromised release, until the signer is pinned. The scripts never use sudo on macOS and never add or remove a quarantine attribute.

## Updates

The only requests Kamapathy's updater makes are a release list, once a day or when asked, and, on request, an installer and its `SHA256SUMS.txt`. They run in an in memory session that sends no cookies, credentials, referrer or cached data, with `User-Agent: Kamapathy` and no version: no identifier, usage data or telemetry. GitHub sees the address and the time, and each installer download adds to GitHub's public count for that file. Certificate errors fail with no exception.

Downloads use HTTPS and URLs fixed to the configured repository's release. The file must match the size the API reported, and its SHA-256 must equal both the release's `SHA256SUMS.txt` and GitHub's own digest; Kamapathy hashes the file again before opening it. Builds are unsigned, so whoever controls the repository's releases could publish a bad installer with matching checksums. That is the same trust as any website download, and it is why Kamapathy never installs by itself.

Kamapathy writes the installer itself rather than through Chromium's download manager, so the file carries no `com.apple.quarantine` attribute or Mark of the Web and Gatekeeper or SmartScreen may not ask again. The install dialog keeps their steps in case they do.

Agents may read the update status, ask for a check and start a download. Opening, installing, cancelling and quitting exist only on shell IPC behind the sender check, so only the person's own click installs anything. A program running as the person could still open the downloaded file, which is inside the account boundary this document describes. Release text is never rendered: the window shows validated versions, sizes and fixed URLs, file names come from the installer naming rule rather than the network, and What's new ships with the app. Release notes open only in a personal space no agent can read. The update test variables are ignored in packaged builds and stripped from starts the client makes.

## Privacy

Kamapathy has no account and no telemetry. It never reports usage, errors or page data anywhere. Its own outbound requests are the ones named above: the daily release check and, when asked, an installer and its checksum file. Both carry no identifier, and the check can be turned off in Settings, under Updates. Everything else leaves the computer because a page or the person asked for it. The install scripts and the website's download buttons read only public release data. History, bookmarks, spaces and settings stay in the profile folder on the computer.

## Release work

Development artifacts are unsigned. Kamapathy can download an update, and the person installs it: while releases are unsigned nothing installs itself, and the installer opens only from the person's own click in Settings. Keep Electron and other dependencies current during development. The signing plan is prepared and dormant: `electron-builder.signed.yml` extends the packaging configuration with a Developer ID identity, the hardened runtime, notarization and `build/entitlements.mac.plist` on macOS, and Azure Trusted Signing on Windows. CI packages with it only once the signing secrets exist, then verifies the signatures, and publishing requires that step once the repository variable `KAMAPATHY_SIGNED_RELEASES` is `true`. Until signing is in place the scripts cannot pin a signer, and a production release still needs broader operating system testing and a security review of browser and automation boundaries.

Kamapathy does not currently provide an extension permission model, credential manager, phishing reputation service, or audited privacy mode. Its separate spaces are not a claim of anonymous browsing.

## Reporting a vulnerability

Use the repository's private vulnerability reporting feature if it is available. Otherwise contact the repository owner through their published contact details and ask for a private reporting channel. Do not publish exploit details or personal profile data in a public issue before maintainers have had a chance to assess the report.

Include the affected Kamapathy version, operating system, minimal reproduction steps using nonpersonal test data, and the boundary you believe is bypassed. Never attach a real browser profile or session cookie.
